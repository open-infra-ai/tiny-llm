> TLLM-P0-004 PR-5 的正式 kernel 级基准。**只测 kernel，不产生 TTFT/TPOT 或 serving
> 结论**（设计包 §9 的 G7 拒绝条件）。

### 1.1 为什么采样参数与 §9 的字面值不同（必须披露）

设计包 §9 写「warmup 20、reps 200（沿用 `kernel_bench` 现有约定）」。**首轮按 reps=200、
每样本 10 次调用实测时，32/32 个 shape 全部因 CV > 10% 判为 `not_converged`**：本机单个
attention kernel 在 S=8 时仅约 2–6 µs，落在 WSL2 的 launch/调度噪声底之上，样本估计量
的方差由 launch 抖动主导，而非 kernel 本身。

因此正式轮改为：**每样本 100 次调用（估计量方差按 1/√n 下降）、每 repeat 1000 次**。
这不是为了让门禁通过而调整阈值——`not_converged` 判定与阈值（CV>10% 或 repeat 中位数
偏差>10%）未变，且 15/32 个 shape 现在仍被判为 `not_converged`（见 §5），全部保留。
runs=200 的那一轮同样保留在交接记录中作为反例。

### 4.1 三条可复现的观察

1. **方向在 3 个 repeat 上完全一致，不是噪声。** 以 bs=16 为例，`direct/legacy` 每个
   repeat 的值：S=128 → 0.745/0.757/0.753（direct 更快）；S=512 → 1.043/1.080/1.024；
   S=1024 → 1.083/1.067/1.087；S=2048 → 1.142/1.148/1.145（direct 更慢）。bs=32 同样一致。
   **交叉点在 S≈129–512 之间**（bs=16 在 129 与 512 之间翻转；bs=32 在 257 与 512 之间）。
2. **分解自洽**：`legacy ≈ gather_k + gather_v + contiguous`。S=2048 时
   `0.0062+0.0063+0.1434 = 0.1559` vs 实测 `0.1510`（差 3.2%）；S=512 差 9.1%。和略微
   偏高是因为三个分量各自作为独立 launch 计时，而 `legacy` 的三次 launch 共享同一个
   采样窗口。这验证了计时口径没有重复计入或漏计。
3. **gather 的绝对开销很小且几乎不随 S 增长**（0.005–0.007 ms）：它是顺序拷贝，
   在 S=2048 也只占 `legacy` 的 **8.3%**（12.5 µs / 151.0 µs），S=512 时占 24.4%。
   **消除它不可能带来两位数百分比的墙钟收益。**

## 5. 收敛与限制（不得隐藏）

| 项 | 结果 |
|----|------|
| 三条**对比路径**（legacy/contiguous/direct）CV ≤ 10% 且 repeat 中位数偏差 ≤ 10% | **17 / 32** |
| 未收敛的 15 个 shape | 全部是 `visible_tokens ≤ 65` 的小窗口（单次 2–8 µs，落在 launch 噪声底）。`visible ≥ 127` 的 shape 全部收敛，legacy CV 1.4%–5.7%、direct CV 1.2%–4.5% |
| 最小/最大值 | 全 shape 上 legacy CV 最大 13.0%、direct 最大 17.2%（均在 S≤65） |
| `gather_k` / `gather_v` 收敛 | **1 / 32**（单次约 5 µs，CV 5.3%–29.2%）——它们是辅助诊断（§9），不参与 shape 级收敛判定，但**逐 path 的 CV 与 repeat 中位数全部保留在原始数据中** |

未收敛的 shape 一律保留、未删除；`not_converged` 与原因写在每个 shape 的
`shape_summary` 记录里。

**限制**：

- 这是 **kernel 级** 测量，未经过 CUDA Graph 捕获。生产 decode 默认开启 CUDA Graphs
  （见 [2026-08-23-cuda-graphs-ab](2026-08-23-cuda-graphs-ab.md)），而 `direct` 相对
  `legacy` 的**唯一优势就是少 2 次 launch**；graph 重放会大幅摊薄 launch 开销，
  因此小窗口下的 `leg/dir ≈ 2.0–2.5` **不能外推为端到端收益**，反而大窗口的劣势
  会完整保留。
- 未测 prefill、batched/ragged decode、非本机硬件；不得外推到大卡或其它模型。
- 单次 5 µs 级别的 gather 在本机噪声底之上，其 CV 不作为收敛证据。
- 未锁频；本机为 WSL2 环境，记录真实抖动。

## 6. 机制：为什么 direct 在长上下文更慢

ncu 2026.2.1.0 在本机**可用**（与 2026-08-23 记录的历史限制不同，见
[对比方法论 §8](../benchmark-methodology.md)），`visible=2048 / block_size=16` 的单次 launch：

| kernel | 时长 (µs) | SM throughput | long-scoreboard stall | DRAM read | L2 | L1 |
|--------|-----------|---------------|----------------------|-----------|-----|-----|
| `attention_decode_paged_kernel`（direct） | 316.0 | 0.86% | 40.2% | 1.16 MB | 7.88 MB | 62.4 MB |
| `attention_decode_kernel`（contiguous） | 279.9 | 0.72% | 45.9% | — | — | — |
| `paged_gather_blocks_kernel` | 4.42 | 26.6% | 66.7% | — | — | — |

ncu 会 replay kernel，绝对值高于墙钟（316 vs 173 µs），**只看比值**：

1. **两条 attention kernel 都是访存延迟受限**（SM throughput < 1%，long-scoreboard
   40%–46%），瓶颈是 `decode_online_softmax` 第 4 步（每个线程固定一个 `d`、遍历整个
   tile）对 V 的低效访问，而不是 DRAM 带宽。
2. **direct 比 contiguous 慢约 13%**（316 vs 280 µs），与墙钟 `cont/direct ≈ 0.83`
   方向一致。这部分是分页寻址自身的代价：`PagedRows::k_row/v_row` 在内层循环里多出
   一次共享内存读（`row_elem`）与一次分支，而 contiguous 只是指针加法。
3. **gather 只有 4.42 µs**，约为 attention kernel 的 1.6%。它省下的 DRAM 流量（可见窗口
   512 KB 量级的 1–2 遍）在 40% 延迟 stall 的循环下**几乎不转化为墙钟**。

因此设计包 §9 的可证伪假设——「legacy 每 step 每 layer 的 K/V 读放大为 direct 的约 2 倍，
所以 direct 应当获益」——**在该假设成立的方向上被证伪**：读放大确实存在，但它的绝对量
（十几 µs）远小于 attention 内层循环的延迟代价，因而被后者淹没。

**profiler 问题的回答**（§9）：direct 不是被 block table 的随机访问在绝对意义上拖慢的
（block table 每 tile 只读一次），而是被**归约内层循环的访存延迟**主宰；分页寻址在此基础上
又叠加了约 13% 的循环内开销。省下的 gather 流量转化为墙钟的比例接近 0。

## 7. 决策与回滚

- 设计包 §10/§11：默认值只在 PR-5 通过后由 `legacy` 改为 `auto`。**本次未通过**，
  因此 **`src/transformer.cpp` 不动，默认值保持 `legacy`**，`auto` 与 `direct` 仍可
  通过 `TLLM_PAGED_ATTENTION` 显式选择（非法值仍显式报错）。
  本 PR 只增加 benchmark 与文档，**没有生产行为变更**。
- §11 的回滚触发条件（逐元素相等门禁失败、sanitizer 报错、真实模型 canary 不一致）
  本轮均未命中；本条结论来自**性能**，不是正确性。
- 未收敛 shape 与失败证据全部保留，未删除、未重跑挑选。

**什么会改变这个结论**（留给后续任务，不在本 PR 范围）：

1. 修掉 `decode_online_softmax` 第 4 步的低效 V 访问（两条路径同受益，但会降低
   gather 占比）——在此之前讨论 direct 的收益没有意义；
2. 在 **CUDA Graph 捕获**下重测：graph 会抵消 direct 唯一的小窗口优势；
3. 更大 `Hq`/`Hkv` 或 head_dim=128 的形状，其中 gather 的相对占比更高；
4. 若将来去掉 direct 路径冗余的 K/V scratch（设计包 §5 的 follow-up），需重新测量。

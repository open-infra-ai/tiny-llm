# 2026-09-15 split-KV decode attention kernel benchmark（RTX 5070 Ti）

> TLLM-ATTN-SPLITKV PR-D 的正式 kernel 级基准。结论先行：split-KV 在
> `visible ≥ ~256`（ns≥2）给出大收益——`S=2048, bs=16` 时 `direct_splitkv@16`
> 比单遍 `direct` 快 **6.03×**、比 `legacy_splitkv@16` 快 1.27×，让 direct 寻址
> 首次明显超过 legacy 全路径；在 `visible ≤ ~129` 的小窗口回退（最多 ~1.9×）。
> 等价性 480/480 全过；`num_splits=1` 与单遍逐位相同，作 anchor。
> **不支持把 `TLLM_ATTN_SPLITKV` 默认值改为 >1**（小窗口回归真实存在，
> 且 host 侧拿不到 device 上的可见长度做自适应）。开关默认保持关闭（单遍）。

## 2. 复现命令

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_CUDA_ARCHITECTURES=native
cmake --build build -j$(nproc) --target tiny_llm_kernel_bench
./build/tiny_llm_kernel_bench --dpa-bench \
  --num-splits 1,2,4,8,16 \
  --warmup 20 --reps 1000 --batch 100 --repeats 3 --clock-warmup 4 \
  --meta dirty_files=0 \
  --out /tmp/splitkv.raw.jsonl

# 单形状隔离（ncu 用）
./build/tiny_llm_kernel_bench --dpa-bench --num-splits 8 \
  --only-visible 2048 --only-block-size 16 --reps 2 --batch 1 --repeats 1 \
  --clock-warmup 0 --out /dev/null

# 汇总
python3 gen_splitkv_summary.py  # /tmp 脚本，输入 raw → summary.json
```

`--num-splits` 语义：逗号分隔，每值 ∈ [1,32]；`1` 走 split-KV 入口但等价
单遍（设计 §5 的 anchor），同时隔离出 combine launch 的固定开销。

### 4.3 读表结论

1. **交叉点 ≈ visible 256**（ns≥2）：`visible ≤ 129` split-KV 稳定回退
   （`S=8` 时 `dsk@16/direct ≈ 0.52`，即慢 ~1.9×）；`visible = 255/256/257`
   `dsk@16` 已快 1.6×；`≥ 512` 全面占优。设计 §9 预估 "交叉点 128–512" 被验证。
2. **最优 ns = 16（本扫描内）**：`visible ≥ 255` 时 @16 ≥ @8 > @4 > @2；
   未测 32（grid 上限内合法，但 @16 的收益曲线已趋平，且更大 ns 的 combine
   成本与 workspace 增大，留给后续需要时再加）。
3. **`num_splits=1` 量化出 combine 固定开销**：`dsk@1` 对单遍 `direct` 的比值
   从 `S=8` 的 ~1.75 单调降到 `S=2048` 的 ~1.03——约一次 4–5 µs 的固定
   launch+kernel 开销（与 §6 ncu 的 5.1 µs combine 时长一致），小窗口上被放大。
4. **split 下取址排序未变**：`S=2048` 时 `contig_sk@16`（0.0266）<
   `dsk@16`（0.0287）< `leg_sk@16`（0.0365）——direct 寻址相对 contiguous
   仍有 ~8% 额外开销，但已远小于 gather 成本；**direct 首次以 kernel 口径
   明确快于 legacy 全路径**（PR-5 单遍时 direct 在 `visible ≥ 512` 反而慢
   3–15%）。

## 5. 收敛与限制（不得省略）

- **32 shape 中仅 4 个所有路径 CV ≤ 10%**（`visible ∈ {1024, 2048} × bs ∈ {16, 32}`），
  与 PR-5 结论一致：**< 30 µs 的小 kernel 在此机时序不稳**。
  `conv=–` 的 median 只作方向性指示；`conv=Y` 的 4 个大窗口 shape 同时是
  split-KV 收益最大的区域，**主要结论（交叉点方向、长上下文加速比）落在收敛区**。
- `visible ≤ 129` 的回归倍数（~0.52–0.72）来自未收敛样本，但全部样本
  方向一致（无一次 split 更快），回归本身可信，精确倍数不保证。
- 只测 `decode=1`；prefill 走 `attention_forward` 不在本路径。
- 未覆盖 `num_splits=32`、`block_size` 其它值、多头 KV（Qwen2.5-0.5B 固定
  n_kv_heads=2）、并发 stream 干扰。

## 6. 机制（ncu，2026-09-14 驱动可用）

`--only-visible 2048 --only-block-size 16 --num-splits 8` 单 launch 指标：

| kernel | µs | `sm__warps_active`（占用率） | `sm__throughput` | long-scoreboard stall | barrier stall | dram bytes |
|---|---|---|---|---|---|---|
| `attention_decode_kernel`（contig） | 281.5 | **8.33%** | 0.72% | 45.6% | 38.8% | 1.08 MB |
| `attention_decode_paged_kernel`（direct 单遍） | 315.5 | **8.35%** | 0.86% | 39.5% | 39.0% | 1.12 MB |
| `attention_decode_paged_splitkv_kernel` @8 | 45.6 | **13.08%** | 6.04% | 41.7% | 35.6% | 1.07 MB |
| `attention_splitkv_combine_kernel` | 5.1 | 5.12% | 0.55% | 65.9% | 0% | 48.6 KB |

回答设计 §9 的待定问题：

- **occupancy 确实被抬起，但没有饱和**：8.35% → 13.08%（≈1.6×，与
  `grid 14→112 block / 70 SM ≈ 1.6 block/SM` 一致）。kernel 仍是
  latency-bound（long-scoreboard ~42%），**收益机制是更多独立 block 的
  并行掩盖了访存+barrier 延迟，而非 occupancy 打满**；SM throughput
  0.86% → 6.04% 直接佐证发射活跃度 ~7×。
- barrier stall 仅 39.0% → 35.6%：block 内 `__syncthreads` 成本仍在，
  但被块间并行稀释到墙钟收益里（45.6+5.1 µs vs 315.5 µs，ncu 口径 ~6.2×，
  与墙钟 @8 的 5.25× 同向）。
- `dram__bytes` 三 kernel 相同（~1.07–1.12 MB）：split-KV 没有引入额外
  显存流量，partial workspace（fp32, ≤59 KB）进出均在 cache 内。
- combine kernel 5.1 µs / 48.6 KB 访存：固定开销小，但在 `S=8` 时占
  总时长 ~40%，是小窗口回归的主因（见 §4.3.3）。

## 7. 决策与回滚

- **不改 `TLLM_ATTN_SPLITKV` 默认值**（保持单遍）：`visible ≤ 129` 回归
  真实且最多 ~1.9×；host 侧无法读 device 上的可见长度做按长度自适应
  （会引入同步），CUDA Graph 下亦不可运行时切换。调用方按场景显式设置
  `TLLM_ATTN_SPLITKV=N`（长上下文推荐 8–16）。
- 若未来需要"自动"，只能在引擎配置期按**已知的最大/典型上下文长度**
  静态选定（env 现有机制），不能在 kernel 内分支——与设计 §11 开放问题一致。
- 回滚方式不变：env 缺省即单遍，`num_splits=1` 逐位等价已验证。
